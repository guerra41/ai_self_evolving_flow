1. The big question

Can software improve its own code? A “self-evolving” system works like this:

  1. Something writes a new version of a program.
  2. The new version is tested and graded.
  3. If it is better, it is kept. If not, it is thrown away.
  4. Repeat.

Research systems such as HyperAgents explore this idea. This project is a small, safe, local version of it. It is not a product. It is a lab bench where you can watch the loop run and see where it breaks.

2. The cast

PartWhat it is
TaskAgentsrc/task-agent/TaskAgent.ts. The program being improved. It solves small text tasks: uppercase, reverse, palindrome, slugify, max number. The starting version is deliberately flawed and scores 63/100.
ProposerA thin wrapper around an LLM. It sends one prompt and gets back a new version of the file. No tools, no memory, no planning. The LLM does all the thinking.
HarnessEverything else: source screen, isolated tests, sandbox, grader, tamper check and archive. This is the real work of the project.
The exameval/. A hidden set of tasks used only for scoring. The Proposer never sees it.

3. The loop

Each generation goes through these steps. Any rejection restores the best code so far, and every path ends in a line in the archive.

  1. The Proposer asks the LLM for a rewritten TaskAgent.
  2. The harness screens the code for forbidden things such as eval, fetch or spawning processes.
  3. The code is tested in an isolated copy.
  4. It is scored on the hidden exam inside a locked-down child process with a timeout and memory limit.
  5. The harness checks that the tests, exam and harness files were not tampered with.
  6. If the score is strictly higher, the code is kept. Otherwise it is rolled back.
  7. One line is appended to outputs/archive.jsonl.

4. What you are really learning

1. Safety is the main subject, not intelligence

Once an AI can edit code that gets run, the hard question is how to stop it from cheating, breaking things or reaching your machine. Most of the project is guardrails:

  • The AI may edit only one folder.
  • Tests gate every change.
  • Generated code runs in a sandbox.
  • The exam stays hidden.
  • Everything is archived.
  • Hashes catch tampering.

Each exists because an AI trying to “win” has easy shortcuts: change the tests, read the answers, hard-code the outputs. The project lets you see that attack surface firsthand.

2. A measurement has to be honest

Before the tie fix, the system said “kept” for changes that did nothing, like deleting a blank line. That looked like progress and was not. Selecting on a score is easy to fool, even by accident, so rules like “strictly higher” matter.

3. The hidden exam creates a real tension

The model cannot see what fails, so it cannot fix it. If you show it the failures it can improve, but then you risk it memorizing the exam, which is a form of cheating. Hiding the exam keeps the score trustworthy but makes improvement hard. There is no free answer, and this tension is a core problem in AI evaluation.

4. Small models cannot do this blind

The 14b model made the same trivial edit 10 times and never found the bugs. The loop needs either a more capable model or better feedback. The harness works; the model is the limit.

5. Who holds the API key

The key stays with the harness, which makes the HTTP call. Generated code runs without it. The LLM never needs the key, and hosted and local models are interchangeable. That is why switching to Ollama took only a few lines.

6. “Tests passed” does not mean “good”

A rewrite can pass every unit test and still be worthless. Tests catch breakage; the exam measures quality. The archive records both so you can see the difference.

5. What the first real run showed

Setup: qwen2.5-coder:14b through Ollama on a laptop, 10 generations.

  • Baseline 63. Every generation scored 63 and was rolled back (“does not improve on the best score 63”).
  • Each generation made the identical change: it deleted one trailing blank line and never touched the faulty code.
  • It repeats because each rollback restores the exact same code, so the model sees the same input at low temperature and gives nearly the same answer.
The harness behaved correctly with a real model. The model was not given enough information to find the bugs, which is the hidden exam doing its job.

6. What it does not show

  • It has not shown AI improving AI. The only real run produced zero improvement. The scripted demo (63 → 75 → 88 → 100) was written by hand to show the loop working. It is not evidence of learning.
  • It is not a complete security boundary. The sandbox does not block network access, the code screen is heuristic, and there is no Docker yet.
  • It is tiny. Five task types is not a general ability.

7. Why it is still worth it

You now have a working, tested loop with real guardrails, where any model can be swapped in. The interesting experiments come next, and each is cheap to run on a laptop:

  • What minimal feedback lets a small model improve without leaking the exam?
  • Does varying the prompt between tries help?
  • Does a bigger model succeed with the same blind setup?
  • Can a second model attack the guardrails to test them?
