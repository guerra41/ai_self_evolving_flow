AI Self-Evolving Flow

A small, safe laboratory for one big question: can software improve its own code automatically, without cheating and without breaking anything?

1The objective

Build a minimal “self-improving” loop, run it on a laptop, and study how it behaves.

Most software only changes when a person edits it. This project asks what happens when an AI edits the code, and the code is then tested and graded automatically, over and over. Each pass is called a generation. We keep the changes that help and throw away the ones that don’t.

What we build

A command-line program (pnpm evolve) that runs the improve-test-grade loop for several generations and saves a record of every attempt.

What we study

Whether the loop really makes the code better, and whether the safety rules around it actually hold when the AI misbehaves.

What we do not build

No website, no database, no product for customers. It is an experiment. The problems it solves are deliberately tiny so we can focus on the loop, not the tasks.

The cast, in everyday terms

Think of a student, a tutor, a rulebook and a final exam.

What the student actually does

The TaskAgent is a small function that solves eight kinds of everyday text and number jobs: make text upper or lower case, reverse it, count words, add up numbers, find the biggest number, check whether a phrase is a palindrome, and turn a title into a web-friendly “slug”. They are easy on purpose. If the jobs were hard, we could not tell whether a failure came from the loop or from the job.

What success looks like The loop runs at least three generations (five by default). Every generation is recorded with its code change, test result, score and time. The score goes up when a good change is proposed. Bad changes are caught and undone. And when we try to make the AI misbehave, the safety rules stop it.

2The problem we are trying to solve

Letting an AI rewrite code is powerful, and risky in five specific ways.

1. It can cheat

If the AI can edit the tests, or peek at the answers, it can raise its score without getting any better. Like a student who changes the answer key.

2. Its code is untrusted

Code the AI writes could try to delete files, read passwords, run other programs, loop forever, or eat all the memory. We cannot assume it is friendly.

3. It can quietly get worse

A change can pass the basic checks and still make the real results worse. Without a rule against this, the code could slowly decay while everything looks fine.

4. Nobody can tell what happened

If nothing is written down, you cannot answer “what changed, why, and did it help?”. A self-changing system you cannot audit is not something you can trust.

The question the project answers Can we build the improve-and-test loop so that it is honest (no cheating), contained (bad code cannot hurt anything), monotone (never accepts a worse version) and auditable (everything is on record)?

Each risk, and what we did about it

4A real run, generation by generation

This is the actual output of pnpm evolve on the project with no API key, using the built-in scripted demo Proposer.

  1. Baseline: 63. The starting code passes every unit test but gets 3 of the 8 hidden exam tasks wrong. This is deliberate: it leaves room to improve.
  2. Gen 1: 75, kept. Fixes “biggest number” for lists of only negative numbers.
  3. Gen 2: rejected. Tries to add a file-reading import. The source screen refuses it before it is saved or run.
  4. Gen 3: 88, kept. Palindrome check now ignores commas and colons.
  5. Gen 4: rolled back. A mistake that turns upper-casing into lower-casing. The unit tests catch it and the old code is restored.
  6. Gen 5: 100, kept. Slugs now keep digits, so “Systems 2026” stays “systems-2026”.
Read this honestly This run uses a scripted stand-in for the AI. Its five steps were written by hand by someone who knew the starting code’s weaknesses. It never reads the exam, but it proves only that the machinery works: baseline, selection, screening, testing and roll-back. It is not evidence that an AI can improve code by itself. That needs a run with a real AI, which has not been done yet.

5The four guardrails

These are the project’s hard rules, from the original brief. Here is each one in plain words, with how it is enforced.

1. Tests first, and a one-file rule enforced

Rule: hand-written tests decide what is acceptable. The AI may change only the one TaskAgent file, never the tests, the grader or the loop.

How: the loop is written to save to exactly one path. Every protected file is fingerprinted at the start and checked again; any difference rolls back the change and stops the run. A change that fails the tests is undone.

2. Sandbox partly enforced

Rule: code written by the AI must never run loose on the main computer. It needs a time limit and a memory limit.

How: it runs in a separate, locked-down child process (no file writing, no starting programs, no secrets) with a 30 s limit, a 256 MB memory limit and an output cap. Docker is not used, and internet access is not blocked. See section 9.

3. Frozen exam enforced

Rule: the AI must never see the exam. It sees only practice prompts and past scores.

How: the exam is read only by the grader. It is not in the AI’s prompt, it is not in the test copy, and the sandbox cannot read outside its temp folder.

4. Archive enforced

Rule: every generation is written down in a simple file, one record per line (JSONL).

How: each line has the generation, code diff, test result, score and time, plus whether it was kept, the best score so far, a run id, and why it was stopped if it was.

6Defensive layers

No single wall is trusted. The AI’s code sits in the middle of several layers, so if one fails another still holds.

What each layer does, in detail

Layer 3 · Source screen before anything runs
Reads the proposed code as text and refuses it if it contains: any import of another module (including built-ins), require, a dynamic import(), process, globalThis, eval or the Function constructor, network calls (fetch, WebSocket), or references to child_process, worker_threads, Deno or Bun. The TaskAgent is a pure calculation, so it never needs any of these. This is a quick filter, not a proof of safety, and clever code could try to disguise itself, which is why the other layers exist.
Layer 2 · Isolated test copy
The unit tests do not run in the real project. The loop builds a temporary copy that holds only the one test file and the TaskAgent, links the installed tools, and runs the tests there with a short allow-list of environment settings (no API key), a time limit and an output cap. The hidden exam is not in the copy. If the test run hangs, the whole family of processes is killed.
Layer 1 · Locked sandbox while grading
Each exam task runs in its own tiny Node.js process started inside an empty temporary folder, using Node’s built-in permission system: no writing files, no starting other programs, no starting workers, reading only that temporary folder. It also has a heap memory limit (256 MB), a hard time limit (30 s, then force-kill), and a cap (1 MB) on how much it may print.
Layer 4 · Tamper alarm
At the start of a run the loop takes a fingerprint (SHA-256 hash) of every protected file: all tests, the exam, the practice prompts, the loop/sandbox/guard code, and the project configuration. After the tests and again after grading it compares. If even one byte differs, the TaskAgent is rolled back, the attempt is recorded with the names of the changed files, and the whole run stops.
Layer 5 · Selection (“never accept worse”)
The starting code is graded first (the baseline). A later version is kept only if it passes the tests and scores at least as high as the best kept so far. Otherwise the best code is restored. Ties are kept. Each attempt is compared with the best kept version, not with the previous attempt, so one bad try cannot lower the bar.
Layer 6 · Archive
One line per attempt, including the failures. You can always answer: what changed, did it pass, what did it score, was it kept, and why not.

7Do the defenses really work? The attack tests

We wrote a deliberately hostile TaskAgent and let it try to break out. Then we ran the very same code without the sandbox, as a control, to prove the attacks were real.

Read a secret file outside its folder (stand-in for the exam)ALLOWEDBlocked
Overwrite a file outside its folder (stand-in for the tests)ALLOWEDBlocked, and the file was checked afterwards: unchanged

Why the control run matters A test that only says “blocked” can be fooled: an earlier version of this check looked successful but was blocking for the wrong reason (it passed an empty file name). The control run shows the same attacks succeed when the guard is off, so a “blocked” result is meaningful.

8The test plan

61 automated tests across 6 files, plus hands-on runs of the real project. Run them with pnpm test (about 90 seconds, because many tests start real processes).

What we test, and why

  1. The student’s skills (14 tests): each of the eight jobs works, plus edge cases such as empty text and empty lists. These are the “rulebook” the AI’s code must always pass.
  2. The guards (13 + 7 tests): the source screen accepts clean code and rejects each forbidden pattern; the fingerprint check detects changed, added and removed files; the secret key is not passed on; timeouts and output caps work; the diff output is correct.
  3. The sandbox under attack (3 tests): the hostile code from section 7, with its control run.
  4. The loop itself (19 tests): a baseline is recorded; a bad proposal is rolled back; a hostile proposal is screened; an AI failure is logged and the run continues; changing a test or the exam stops the run; a lower score is rolled back; a tie or improvement is kept; run ids are distinct. Includes the isolated test runner.
  5. The whole thing, end to end (5 tests): the scripted demo runs five real generations and must produce exactly 63, 75, rejected, 88, rolled back, 100.

How we make sure the tests can actually fail

  • Control runs. The attack test runs the same hostile code unprotected and expects it to succeed.
  • Regression tests that fail without the fix. For the Windows drive-letter bug (section 10) we removed the fix and confirmed the test fails, then restored it.
  • Real outcomes, not just return values. The write-attack test re-reads the target file from disk to prove it was not changed.
  • Real processes. Timeout and output-cap tests start real child processes and really kill them.

Hands-on checks beyond the automated tests

  • pnpm evolve run on the real project with the scripted Proposer: baseline 63, then 75, rejected, 88, rolled back, 100.
  • A run where a deliberately broken generation was rolled back and a later good one was kept.
  • Checks after each run that the real dependencies were not deleted by clean-up and that no stray processes were left.
  • A browser check is not applicable: there is no web interface by design.

9Known limits: what this does not prove

A safety document that only lists strengths is not trustworthy. These are the gaps.

The internet is not blocked Node’s permission system does not restrict network access. The source screen forbids network calls and the key is hidden, but a determined piece of code could still try. Full isolation would need Docker with networking turned off.
The source screen is a filter, not a proof It matches words and patterns. Obfuscated code could slip past it, which is exactly why the sandbox, the isolated copy and the fingerprint check also exist.
The test phase is not permission-locked The unit tests run in an isolated copy with no secrets, but not inside the stricter permission sandbox (the test framework needs more freedom than that). The screen and the fingerprint check cover that gap.
The real AI has not run yet Everything here was shown with a scripted stand-in. Whether a real model can raise the score, and how it behaves when it fails, is the actual experiment, and it is still to do.
Smaller things
  • The Linux/macOS version of “kill the whole process family” is written but has only been run on Windows.
  • The tiny task set (8 jobs) can be solved fully; a real study needs harder, more varied tasks.
  • The loop changes the code file in place. After a run the file holds the best version; reset it with git checkout -- src/task-agent/TaskAgent.ts.
  • The repository on GitHub is public, so the code and these notes are visible to anyone.

10What the tests taught us

Writing the tests exposed real problems. That is the point of testing.

Orphaned processes

On a timeout only the main process was killed. The test framework’s helper processes kept running and locked the temp folder. Now the whole process family is killed.

A check that proved nothing

An early “it is blocked” check was blocking because of an empty input, not because of the sandbox. The new attack test has a control run to prevent this.

Windows drive letters

The test framework failed when the project path used d: instead of D:, because it loaded itself twice. The loop now links tools through their canonical path, with a regression test.

How to run it

  1. Install: corepack enable, then pnpm install, then copy .env.example to .env. Needs Node.js 22.3 or newer.
  2. Run the tests: pnpm test.
  3. Watch the loop with no key: pnpm evolve. To use a real AI, put OPENAI_API_KEY in .env.
  4. Tune the guardrails in .env: EVOLUTION_GENERATIONS, SANDBOX_TIMEOUT_MS, SANDBOX_MEMORY_MB.
  5. Run again from the starting code: git checkout -- src/task-agent/TaskAgent.ts.

Glossary

Generation
One pass of the loop: propose, check, grade, keep or undo. Generation 0 is the starting code.
Baseline
The score of the starting code. Every later version must at least match the best score so far.
Proposer
The small piece of our own code that asks an LLM to suggest a new version of the code, and hands the answer to the loop. The LLM does the thinking; the Proposer is a thin wrapper around it (about 60 lines). It makes one request per generation and has no tools or planning of its own. The original brief called it the “MetaAgent”; we renamed it because it is closer to a request-and-extract step than to an agent.
TaskAgent
The code being improved: one plain function that solves the eight jobs.
Frozen exam (eval set)
A fixed set of graded tasks the AI is never shown, so a good score cannot come from memorizing it.
Roll back
Restore the previous best code after a rejected attempt.
Sandbox
A locked room for running untrusted code: it can compute, but cannot reach the rest of the computer.
Hash / fingerprint
A short code computed from a file’s contents. If the file changes by even one character, the fingerprint changes.
Source screen
A text scan that rejects code containing forbidden words before it is ever executed.
JSONL
A plain text file with one small record per line. Easy to read, search and process.
Control run
The same test with the protection switched off, to show the test would notice a failure.
Process tree
A program together with every helper program it started.
